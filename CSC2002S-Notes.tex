\section{Parallel and Concurrent Programming}
\subsection{What is parallel computing?}
\subsubsection{Changing a core assumption}
So far, all algorithms have assumed that one thing happens at a time. This is traditional sequential programming.
We have to change the core assumption. Multiple activities may be in process concurrently, and some may execute simultaneously in parallel.
Parallel and concurrent programming remove the requirement that all computational steps belong to one global serial order.
\begin{definition}[Commonly used terms]
In most conventional usage,
\begin{itemize}
    \item \textbf{Parallel} programming focuses on arranging that multiple activities co-occur.
    \item \textbf{Distributed} programming focuses on arranging thta activities occur in different places.
    \item \textbf{Concurrent} programming focuses on interactions of ongoing activities with each other.
\end{itemize}
However, all three terms may apply in most contexts.
\end{definition}
\subsubsection{Parallelism versus concurrency}
\textbf{Parallel program:}\\
Use extra computational resources to solve a problem faster by performing multiple computations simultaneously.
\\\\
\textbf{Concurrent program:}\\
Allow multiple activities to be in process during the same period of time.
\subsubsection{Parallel algorithm example}
Here is the pseudo-code for an array sum algorithm:
\begin{lstlisting}[language=Java]
public int parallelSum(array, workers):
    partial = new array[workers];

    PARALLEL FOR worker = 0 to workers - 1 {
        lo = worker * array.length / workers;
        hi = (worker + 1) * array.length / workers;
        partial[worker] = sequentialSum(array, lo, hi);
    }

    return sequentialSum(partial, 0, workers);
\end{lstlisting}
\begin{warning}[Parallel workers]
With $p$ workers, the theoretical upper bound for the parallel summation phase is approximately $p$, but the actual speedup will usually be slower because of:
\begin{enumerate}
    \item thread-management overhead,
    \item memory bandwidth,
    \item load imbalance, and
    \item the final sequential combination.
\end{enumerate}
\end{warning}
\subsubsection{Concurrency example}
For example, multiple operations on a hash table.
What could go wrong if two threads update the same bucket at the same time?
\begin{enumerate}
    \item Lost updates;
    \item Corruption of a bucket chain or tree;
    \item Duplicate entries despite a uniqueness invariant;
    \item A lookup observing a partially constructed state;
    \item Resizing while another operation uses the old table;
    \item etc.
\end{enumerate}
Here is the pseudo-code for a shared hash table:
\begin{lstlisting}[language=Java]
public void insert(key, value):
    bucket = findBucket(key)

    /* Acquire protection for bucket */
    /* Perform insertion */
    /* Release protection for bucket */
\end{lstlisting}
\begin{note}[Shared hash table]
\begin{itemize}
    \item Prevent bad interleaving (correctness)
    \item But allow some concurrent access (performance)
\end{itemize}
\end{note}
\subsubsection{Restaurant analogy}
A serial program is a recipe for one cook. The cook does one thing at a time (sequential), maybe switching between tasks (time-slicing).
Options for lots of cooks:
\begin{itemize}
    \item use helpers to assist with a big task, like slicing lots of potatoes for hot chips \textbf{(data parallelism)}.
    \item dedicate helpers to different taks, such as beating eggs, slicing onions, washing up \textbf{(concurrency)}.
    \item have a list of taks and assign them to workers as they are free \textbf{(worker pool)}.
    \item But too many chefs mean too much time coordination which leads to them bumping into each other etc.
\end{itemize}
Often there are multiple steps that can be done at the same time with access to more cooks. More cooks require extra coordination.
A cook may have to wait for another cook to finish something. There are limited resources.
\begin{itemize}
    \item If you only have one oven, two cooks won't be able to bake cakes at different temperatures at the same time.
    \item Some recipes will require exclusive use of the oven.
\end{itemize}
One approach is to allow access to the oven, but only one at a time (cakes can flop). Cooks must wait until the oven is free.
\begin{lstlisting}[language=Java]
if (!ovenBusy) {
    ovenBusy = true;
    bakeCake();
    ovenBusy = false;
}
\end{lstlisting}
\begin{warning}[Pseudo-code issue]
This specific pseudo-code is fine for a single-threaded program, but will it work for a multi-threaded program?
\end{warning}
\subsubsection{Race conditions}
\begin{definition}[Race condition]
A \textbf{race condition} is an error where the correctness of a program depends on the relative timing or interleaving of concurrent operations.
\end{definition}
$\quad$\\[-1em]
The idea is that the events race each other. A particular execution may appear correct even though the race condition is present.
Uninteded race conditions are incredibly common in concurrent programs.
\subsubsection{Non-determinism}
\textbf{Deterministic:}\\
In a simple sequential program, instructions are executed in a fixed order determined by the program and its input. 
The execution of one procedure does not overlap in time with another.
\\\\
\textbf{Non-deterministic:}\\
In concurrent programs, there are many possible interleavings. The exact interleaving is generally not predictable. 
Non-deterministic scheduling does not imply an incorrect or unpredictable final result, but a correct concurrent program should satisfy its specification under every permitted interleaving.
\subsubsection{When is concurrent programming necessary?}
Complex systems like:
\begin{itemize}
    \item \textbf{operating systems},
    \item \textbf{web browsers},
    \item \textbf{real-time} systems,
    \item \textbf{event-based} implementations of graphical user interfaces,
    \item multiuser \textbf{games}, \textbf{chat} and \textbf{e-commerce}
\end{itemize}
handle mutiple things happening at once and are therefore multi-threaded. These systems must respond to multiple ongoing activities.
Their tasks may be interleaved on one core or executed in parallel on several cores.
\subsubsection{Moore's law}
Between 1980-2005, Moore's law held:
\begin{itemize}
    \item clock speeds of desktop computers doubled every 18-24 months
    \item exponentially faster at running sequential programs
\end{itemize}
But, it eventually reached
\begin{itemize}
    \item \textbf{Power wall:} increasing frequency and transistor activity produce excessive power use and heat.
    \item \textbf{Memory wall:} processor performance improved faster than memroy-access latency and bandwidth.
\end{itemize}
\subsubsection{Concurrency does not require multiple cores}
On one logical processor, runnable threads take turns through scheduling and pre-emption. Their executions are interleaved.
On multiple logical processors, several threads may execute simultaneously. The operating system and runtime control processor scheduling.
\subsubsection{High performance computing (HPC)}
HPC uses cutting-edge parallel computers to solve "grand-challenge" (computational) problems.
Programmers write programs to solve such computationally large problems that it would take years, or centuries, for one computer to finish it.
\\\\
\textbf{Deep learning:}\\
The modern growth of deep learning was enabled by:
\begin{itemize}
    \item large training datasets;
    \item algorithmic advances;
    \item GPUs and specialized accelerators;
    \item efficient parallel software frameworks;
    \item large-scale distributed computing.
\end{itemize}
\textbf{Weather forecasting and climate modelling:}\\
Weather models divide the atmosphere and oceans into a three-dimensional grid. Each grid cell requires repeated calculations of temperature, pressure, moisture, wind, radiation, and fluid movement.
Cells interact with neighboring cells, so the calculations is both highly parallel and communication-intensive.
\\\\
\textbf{Molecular modelling:}\\
Molecular modelling simulates the behavior and interactions of molecules to try to understand their properties.
It is widely used in drug development.
\\\\
\textbf{Animations and visual effects:}\\
Typically, animation studios need HPC systems. Computer graphics must be rendered into high-resolution images.
Rendering turns a virtual 3D scene into a 2D image, and requires a lot of computational power.
\begin{note}[Note]
While HPC as a concept should be known, the "in-between" bits for deep learning, forecasting, molecular modelling, etc. are not necessarily examinable.
\end{note}

There is a single virtual address space across all of memory. Each processor can access all locations in memory.

\subsubsection{Cache}
A memory cache, also called a "CPU cache," is a memory bank that stores recently used instructions and data close to the processor.
\begin{itemize}
    \item Is had faster static RAM (SRAM) chips than the dynamic RAM (DRAM) used for main memory.
    \item The cache allows instructions to be executed and data to be read and written at higher speed.
\end{itemize}
Modern chips can have multiple caches (L1, L2, L3):
\begin{itemize}
    \item The L1 cache is the fastest.
    \item Each subsequent cache is slower but larger than L1.
    \item Instructions and data are staged from main memory to L3 to L2 to L1 to the processor.
    \item One multicore chips, the L3 cache is generally shared among all the processing chips.
\end{itemize}
Why do caches matter for PCP? If two cores repeatedly modify the same variable, their caches continually invalidate one another.

\begin{definition}[Process]
A \textbf{process} is an operating system unit of resource allocation both for CPU time and for memory.

\begin{itemize}

    \item global/static data
    \item heap
    \item stack
\end{itemize}
Generally, each process in an operating system has its own address space.

\subsubsection{Parallel program}
The shared memory model has multiple explicit threads running concurrently. Threads can:
\begin{itemize}
    \item perform multiple computations in parallel;
    \item perform separate simultaneous activities;
    \item communicate implicitly by reading and writing shared memory.
\end{itemize}

\subsubsection{Sequential program state}
A running serial program has:
\begin{itemize}
    \item \textbf{One program counter}
    \item \textbf{One call stack}
    \begin{itemize}
        \item Each stack frame holds the local variables for a method call that has started but not yet finished.
        \item Calling a method pushes a new frame and returning from a method pops a frame.
        \item Call stacks are why recusion is not "magic."
    \end{itemize}
    \item \textbf{Objects}
    \begin{itemize}
        \item Objects are created by calling \textbf{new}.
        \item We call the memory that holds all the objects the heap.
    \end{itemize}
    \item \textbf{Static fields of classes.}
\end{itemize}
\subsubsection{Programming model: shared memory}
Each thread has its own program counter, call stack, and local variables.
All threads share one collection of objects and static fields.
Static fields of classes are also shared by all threads.
Threads communicate through shared objects (implicit communication). 
Threads communicate by writing data that another thread later reads.

\subsubsection{How threads run}
As the programmer, you create the threads. The operating system scheduler determines how and when those threads are run on the available processors.
Unless you are writing the scheduler, \textbf{you do not have control over this}.
You don't how how many processors/cores your program will use (you can guess).
You don't how the order in which threads will execute (you can not guess).
\begin{warning}[Super important]
Never write code that depends on thread execution order!
\end{warning}

    \item \textbf{Garbage collection} (really, really long: milliseconds to seconds)
\end{itemize}

\subsection{Multi-threading in Java}
\subsubsection{Java is always multi-threaded}
The Java Virtual Machine (JVM) executes as a process under the operating system.
In Java, every program has more than one thread. It starts with one thread, called the main thread.
The main thread can then create additional threads.
The JVM also creates system threads to perform tasks such as:
\begin{itemize}
    \item garbage collection,
    \item signal handling,
    \item JIT compilation,
    \item etc.
\end{itemize}
\begin{figure}[H]
    \centering
    \includegraphics[width=0.5\linewidth]{Pictures/pcp_10.png}

\subsubsection{Basic threads in Java}
All threads are associated with an instance of the class \textbf{java.lang.Thread}.
There are two basic strategies for using the Thread class:
\begin{enumerate}
    \item create a Thread object each time the application needs to initiate an asynchronous task, or
    \item pass the application's tasks to an executor (\textbf{java.util.concurrent}) that will launch and manage the threads.
    This is the standard approach for parallelization. Uses a high-level API to manage a thread pool for large-scale applications that run on multi-processor and multi-core systems.
\end{enumerate}
There are two ways to create a basic thread in Java:
\begin{enumerate}
    \item Extend the Thread class (\textbf{java.lang.Thread}). Easy for simple programs.
    \item Implement the Runnable interface in an object and pass that to a thread's constructor (\textbf{java.util.Runnable}). This is the more general and flexible approach.
\end{enumerate}
\subsubsection{Thread class}
A Thread class manages a single sequential thread of control. Threads may be created and deleted dynamically.
The Thread class executes instructions from its method \textbf{run()}.
The actual code executed depends on the implementation provided for \textbf{run()} in a derived class.

\subsubsection{Stopping a thread}
Most of the time, we allow threads to stop by running to completion.
Sometimes we want to stop threads sooner, e.g. when the user cancels an operation.
It is not very easy to get threads to stop safely, quickly, and reliably.
\textbf{Thread.stop()} and \textbf{Thread.suspend()} are too dangerous and was deprecated.
Instead, ask the thread to stop by using an interupt.
\subsubsection{Java executors for parallel programming}
Executor objects in Java distribute tasks to worker threads in a thread pool.
Thread pools reduce thread creation overhead since allocating and deallocating many thread objects require significant memory management.
There are three executor interfaces in Java. We primarily focus on \textbf{Fork/Join}.
The Fork/Join executor is designed for divide-and-conquer algorithms especially thos that are recursive.
It uses the "work-stealing" algorithm, where idle threads can steal tasks from busy threads.
\textbf{ForkJoinPool} is the main thread pool class. There are two types of tasks sent to the pool.
\begin{itemize}
    \item \textbf{RecursiveAction} has no return value, and
    \item \textbf{RecursiveTask} returns a value.
\end{itemize}

\subsubsection{Fork/Join framework}
\begin{note}[Important distinction]
A \textbf{task} describes \textbf{work}. A \textbf{worker} thread executes \textbf{work}.
\end{note}
\begin{note}[Note]
\textbf{ForkJoinTasks} (either RecursiveAction or RecursiveTask) are given to a \textbf{ForkJoinPool} (a pool of threads).
\end{note}
$\quad$\\[-1em]
There are two ways to creatre a ForkJoinPool. 
\\\\
\textbf{Option 1:}
\begin{lstlisting}[language=Java]
static final ForkJoinPool fjPool = new ForkJoinPool();
\end{lstlisting}
Here, \textbf{ForkJoinPool()} creates a pool with parallelism equal to \textbf{Runtime.availableProcessors()}, i.e. the total number of processors in your machine.
Importantly, you can specify the parallelism with
\begin{lstlisting}[language=Java]
new ForkJoinPool(int p)
\end{lstlisting}
$\quad$\\[-1em]
\textbf{Option 2:}
\begin{lstlisting}
static final ForkJoinPool fjPool = new ForkJoinPool.commonPool();
\end{lstlisting}
Here, \textbf{commonPool()} creates a pool with parallelism equal to \textbf{Runtime.availableProcessors()-1}, i.e. one less than the total number of processors in your machine.

\subsection{Parallel algorithms}
\subsubsection{Divide-and-conquer: reductions}
Reduction operations produce a signle answer from a collection via an associative operator, e.g. \textbf{max}, \textbf{count}, \textbf{left-most}, \textbf{sum}, etc.
Recursive results don't have to be single numbers of strings. They can be arrays or objects with multiple fields.
\subsubsection{Divide-and-conquer: maps}
A map independently transforms every input element, producing one output element for each input element. There is no combining of results.
A canonical example: vector addition
\begin{lstlisting}[language=Java]
public int[] vector_add(int[] arr1, int[] arr2) {
    assert (arr1.length == arr2.length);
    result = new int[arr1.length];

    for (int i=0; i<arr1.length; i++) {
        result[i] = arr1[i] + arr2[i];
    }

    return result;
}
\end{lstlisting}

\subsubsection{Parallel prefix-sum}
The parallel prefix-sum does two passes. The first pass builds a tree bottom-up: a reduction pass to compute subtree sums.
The second pass traverses the tree top-down: a distribution pass to propogate the accumulated value from the left.
\begin{figure}[H]
    \centering
    \includegraphics[width=0.6\linewidth]{Pictures/pcp_33.png}
\end{figure}
$\quad$\\[-1em]
\textbf{Algorithm: part 1}\\
Build a binary tree where:
\begin{itemize}
    \item The root has sum of the range $[x,y)$.
    \item If the range contains more than one element, i.e. $\text{hi}-\text{lo}>1$:
    \begin{itemize}
        \item Left child has sum of $[\text{lo},\text{mid})$.
        \item Right child has sum of $[\text{mid},\text{hi})$.
        \item A leaf has sum of $[i,i+1)$, i.e. \textbf{input[i]}.
    \end{itemize}
\end{itemize}
\textbf{Algorithm: part 2}\\
Pass down a value \textbf{fromLeft}:
\begin{itemize}
    \item Root given a \textbf{fromLeft} of 0.
    \item Node takes its \textbf{fromLeft} value and
    \begin{itemize}
        \item Passes its left child the same \textbf{fromLeft}.
        \item Passes its right child its \textbf{fromLeft} plus its left child's \textbf{sum}.
    \end{itemize}
    \item At the leaf for array position $i$, \textbf{output[i] = fromLeft[i] + input[i]}.
\end{itemize}

\subsection{Parallel performance}
\subsubsection{Demonstrating parallel performance}
To justify their existence, parallel algorithms must be both correct and efficient.
To demonstrate correctness, you validate an algorithm against the serial version to show that it produces the same results across a range of inputs.
To demonstrate efficiency, you benchmark an algorithm against the serial version, to show that it is faster.
\subsubsection{Speedup}
The speedup expected with $P$ processors is equal to the time to solve problem size $n$ with 1 thread divided by the time to solve problem size $n$ with $P$ threads.
$$
S_P=\frac{\text{time to solve }n\text{ with 1 thread}}{\text{time to solve }n\text{ with }P\text{ threads}}=\frac{T_1}{T_P}
$$
\begin{figure}[H]
    \centering
    \includegraphics[width=0.6\linewidth]{Pictures/pcp_39.png}
\end{figure}
\begin{warning}[Note]
To compare parallel performance, you need to show speedup graphs and not time graphs!
\end{warning}
$\quad$\\[-1em]
Perfect linear speedup is when $S_P=P$. In this case, doubling $P$ halves the running time.
However, this is hard to achieve in practice. Most algorithms reach an optimal level of performance and then deteriorates.
\begin{figure}[H]
    \centering
    \includegraphics[width=0.6\linewidth]{Pictures/pcp_40.png}
\end{figure}
$\quad$\\[-1em]
Superlinear speedup is when $S_P>P$. This is generally not possible in the simple ideal model where the same work is performed and memory effects are ignored.
It can occasionally occur in practice due to:
\begin{itemize}
    \item cache effects / memory hierarchy,
    \item different algorithmic behavior or
    \item measurement artifacts
\end{itemize}
Scalability describes how well performance continues to improve as we increase the processor count and/or the problem size.
\subsubsection{Parallel efficiency}
Speedup tells us how much faster a program is running.
Efficiency tells us how effectively we are using available processors, where perfect efficiency is 100\%.
$$
E_P=\frac{S_P}{P}=\frac{T_1}{PT_P}
$$
As we add processors, speedup may continue to increase, while efficiency decreases. For example,
\begin{itemize}
    \item Speedup of 6 on 8 cores: $E_8=75\%$.
    \item Speedup of 6 on 32 cores: $E_{32}=18.75\%$.
\end{itemize}
\subsubsection{Theoretical analysis of expected speedup}
There are two key measures of runtime:
\begin{itemize}
    \item Work ($T_1$): how long would it take 1 processor. The serial time e.g. for divide-and-conquer, just "sequentialize" the recursive forking.
    \item Span ($T_\infty$): how long it would take on an ideal machine with unlimited processors. Also called the "critical path length" or "computational depth."
\end{itemize}
The maximum possible speedup is $T_P=\frac{T_1}{T_\infty}$, i.e. work divided by span.
Parallel algorithms are about decreasing span without increasing work too much.
\begin{note}[Note]
For theoretical work/span analysis, $T_1$ is the time taken by the parallel algorithm on one processor. For experimental evaluation, speedup is measured against the best appropriate serial implementations:
$$
S_P=\frac{T_{\text{serial}}}{T_{\text{parallel},P}}
$$
Always state which baseline you use.
\end{note}
\subsubsection{Limits on $T_P$}
\textbf{Work law:}
$$
\boxed{T_P\geq\frac{T_1}{P}}
$$
Each processor executes at most 1 instruction per unit time, and hence $P$ processors can execute at most $P$ instructions per unit time.
Thus, to do all the work on $P$ processors, it must take at least $T_1/P$ time.
\\\\
\textbf{Span law:}
$$
\boxed{T_P\geq T_\infty}
$$
A finite number of processors cannot outperform an infinite number of processors, because the infinite processor machine could just ignore all but $P$ of its processors and mimic a $P$ processors machine exactly.
\subsubsection{The DAG (cost graph)}
Program execution can be seen as a DAG where nodes are the pieces of work and edges indicate either a fork or a join.
\begin{figure}[H]
    \centering
    \vspace{-20px}
    \includegraphics[width=0.25\linewidth]{Pictures/pcp_41.png}
\end{figure}
$\quad$\\[-1em]
The work ($T_1$) is the total number of nodes in the DAG.
The span ($T_\infty$) is th elongest path in the DAG.
The set of instructions form the vertices of the DAG, and the graph edges indicate dependence between instructions.
We say that instruction $x$ precedes an instruction $y$ if $x$ must complete before $y$ can begin.
\subsubsection{Divide-and-conquer parallel algorithms}
\textbf{fork} and \textbf{join} are very felxible, but divide-and-conquer maps and reductions use them in a very basic way.
\begin{figure}[H]
    \centering
    \includegraphics[width=0.5\linewidth]{Pictures/pcp_42.png}
\end{figure}
$\quad$\\[-1em]
The work is $O(N)$ and the span is $O(\log N)$. Therefore, the maximum speedup is $O(N/\log N)$.
As $N$ increasesm the available parallelism $N/\log N$ becomes very large.
With enough processors, this algorithm therefore has substantial theoretical parallelism.
Anything that can use results from two halves and merge them in $O(1)$ time has the same property.
\begin{figure}[H]
    \centering
    \includegraphics[width=0.7\linewidth]{Pictures/pcp_43.png}
\end{figure}
$\quad$\\[-1em]
For well-structured fork/join computations, the framework has expected running time
$$
T_P=O(T_1/P)+O(T_\infty)
$$
The first term dominates for relatively small $P$, and the second for sufficiently large $P$.
It's only an "expected" result because internally the framework uses randomness.
\subsubsection{Why measured speedup falls below the ideal}
Parallelization overhead is the time required to coordinate parallel tasks, as opposed to doing useful work. For example:
\begin{itemize}
    \item task creation
    \item task scheduling/allocation
    \item fork/join operations
    \item syncronization
    \item load imbalance
\end{itemize}
Hadware effects:
\begin{itemize}
    \item cache misses
    \item memory bandwidth
    \item contention
\end{itemize}
\subsubsection{Where does scaling stop?}
As the number of processors $P$ increases:
\begin{itemize}
    \item \textbf{Initially:} useful parallel work dominates, i.e. $T_P=T_1/P$. Speedup may be close to linear.
    \item \textbf{Then:} parallel overheads and hardware effects become significant, e.g. task scheduling, joins, load imbalance, cache misses, memory bandwidth.
    \item \textbf{Eventually:} the serial portion / span limits further improvement. Adding processors gives smaller and smaller gains.
    \item \textbf{Beyond this point:} extra processors may actually make the program slower.
\end{itemize}
\subsubsection{Amdahl's law}
Amdahl's law is a performance model/law that demonstrates the diminishing returns of adding more processors.
$$
S_P=\frac{1}{(1-p)+\frac{p}{P}}
$$
Typically, some parts of the program parallelize well, e.g. maps/reductions over arrays. We call this the parallel fraction $p$.
Some parts of the program are inherently sequential, e.g. reading a linked list, getting input, reading from a file, doing computations where each step needs the previous step, etc.
We call this the serial fraction $s=1-p$.
In terms of work and span, this means that the serial portion restricts the minimum span, thus
$$
T_\infty\geq (1-p)T_1
$$
and so, the maximum possible speedup is:
$$
\frac{T_1}{T_\infty}\leq\frac{1}{1-p}
$$
For example, ten processors with 60\% parallelizable and 40\% sequential. How close are we to a 10-fold speedup?
$$
S_{10}=\frac{1}{0.4+\frac{0.6}{10}}=2.17
$$
Now, ten processors with 99\% parallelizable and 1\% sequential. How close are we to a 10-fold speedup now?
$$
S_{10}=\frac{1}{0.01+\frac{0.99}{10}}=9.17
$$

\subsubsection{Gustafson's law}
Amdahl's law assumes that the total problem size remains fixed as processors are added.
In practice, additional computing power is often used to solve larger problems in approximately the same elapsed time.
The additional work is often predominantly parallel, so the serial fraction becomes less important as the problem size grows.
\subsubsection{Scaling with problem size}
Parallel performance depends stringly on the size of the problem.
\begin{itemize}
    \item A parallel program may perform poorly for small problems because:
    \begin{itemize}
        \item there is too little useful work to offset the parallel overhead;
        \item task creation, scheduling and \textbf{join()} costs dominate.
    \end{itemize}
    \item As the problem becomes larger:
    \begin{itemize}
        \item there is more useful work available to divide between processors;
        \item parallel overhead becomes a smaller fraction of the total runtime;
        \item speedup may therefor increase with problem size.
    \end{itemize}
    \item But eventually:
    \begin{itemize}
        \item memory bandwidth, cache capacity, memory use or other hardware limitations may become important.
    \end{itemize}
\end{itemize}
\subsubsection{Grid simulations}
Increasing the grid dimensions can increase the work in more than one way.
For a $R\times C$ simulation, the work per timestep is directly proportional to $R\cdot C$, but the total work is approximately:
$$
\boxed{\text{total work}\propto R\times C\times \text{number of timesteps}}
$$
If larger grids also require more timesteps to reach convergence, runtime can grow faster than the number of cells alone suggest.
\\\\
\textbf{For example:}\\
In an $N\times N$ grid:
\begin{itemize}
    \item doubling $N$ gives 4 times as many cells;
    \item if it also takes roughly 2 times as many timesteps;
    \item total work becomes 8 times larger.
\end{itemize}
\subsubsection{Two kinds of scaling}
There are two types of scaling.
\\\\
\textbf{Strong sclaing (Amdahl's law):}
\begin{itemize}
    \item fixed problem size
    \item defined as how the solution time varies with the number of processors for a fixed total problem size.
    \item For example, same task with double the number of processors.
\end{itemize}
$\quad$\\
\textbf{Weak scaling (Gustafson's law):}
\begin{itemize}
    \item fixed problem size per processor.
    \item defined as how the solution time varies with the number of processors for a fixed problem size per processor.
    \item For example, double the task when you double the number of processors.
    \item Efficiency:
$$
E_P=\frac{\text{time to solve problem size }n\text{ with 1 thread}}{\text{time to solve problem size }n\times P\text{ with }P\text{ threads}}
$$
\end{itemize}

\subsubsection{What is architecture?}
Computer architecture is a study of the overall structure and function of computer systems. In other words, how hardware components link and interact with software.

\subsubsection{Assembly programming}
A useful lens for understanding computer systems. It exposes the hardware but still (somewhat) device independent.

    \item \textbf{Input} writes data from an external source to memory, and \textbf{output} reads data from memory and transmits to an external source.
    \item \textbf{Control} sends the signals that determine the operations.
    \item The \textbf{datapath} performs the data processing.
\end{itemize}

    \centering
    \includegraphics[width=0.3\linewidth]{Pictures/arch_1.png}
\end{figure}

\subsubsection{Measuring performance}
The performance equation:
$$
\boxed{\text{Runtime}=\text{IC}\times\text{CPI}\times\text{Clock Cycle Time}}
$$
where:
\begin{itemize}
    \item $\text{IC}$ is the instruction count, i.e. the total number of instructions in the program.
    \item $\text{CPI}$ is the number of cycles per instruction, i.e. the average number of clock cycles required for an instruction.
    \item $\text{Clock Cycle Time}=\frac{1}{\text{Clock Rate}}$ is the time for one processor clock period.
\end{itemize}
This is an approximation of the actual measured runtime, but reasonably accurate.

\subsubsection{Performance fallacies}
Using a subset of the performance equation is problematic. The clock rate:
$$
\text{Clock Rate}=\cancel{\text{IC}\times\text{CPI}}\times\text{Clock Cycle Time}
$$
For example, the Intel Core i7-3770K has a clock rate of 3.9GHz. Different architectures may require different numbers of cycles for the same instructions.
MIPS = Millions of Instructions Per Second:
$$
\text{MIPS}=\cancel{IC}\times\text{CPI}\times\text{Clock Cycle Time}
$$
For example, the Intel Core i7-3770K can run 106924 MIPS. Different architectures has different instruction sets, so it cannot be used to directly compare program performance.

\begin{lstlisting}

\end{lstlisting}
Here is a simple MIPS addition program:
\begin{lstlisting}[language=Python]
.data                       # Declare memory and constants
    num1:   .word   12      # Store 12 at memory location "num1"
    num2:   .word   13      # Store 13 at memory location "num2"
    num3:   .word   0       # Store 0 at memory location "num3"
.text                       # Code section
.globl main                 # Declare the label "main" as global

# Program that loads words from memory and stores words to memory

main:                       # Label "main" (starting point)
    lw      $t1, num1       # Load the value of num1 (12) in $t1
    lw      $t2, num2       # Load the value of num2 (13) in $t2
    add     $t3, $t1, $t2   # $t3 = $t1(12) + $t2(13) = 25
    sw      $t3, num3       # Store the value in $t3 (25) in num3

exit:                       # Label "exit"
    li      $v0, 10         # Load service 10 (terminate program)
    syscall                 # Perform system call with service 10.
\end{lstlisting}

\subsubsection{Labels}
The notation of variables is a high-level programming concept not available in MIPS assembly. Instead, labels are used to identify addresses in data and code, e.g. "main" in code and "num1" in data.
Importantly, RISC arithmetic and logic instructions do not operate on data memory directly but on registers instead. So, transfer from data memory to registers is a must!

\subsection{Regular Languages}
\subsubsection{Finite automata}
\begin{definition}[Finite automata]
A \textbf{finite automaton} is a 5-tuple $(Q,\Sigma,\delta,q_0,F)$ where:
\begin{itemize}
    \item $Q$ is a finite set of all possible states.
    \item $\Sigma$ is a finite set of all alphabet symbols.
    \item $\delta$ is a transition function $\delta:Q\times\Sigma\to Q$. In other words,
    \begin{figure}[H]
        \centering
        \includegraphics[width=0.3\linewidth]{Pictures/finite_auto_2.png}
    \end{figure}
    \item $q_0$ is the start state.
    \item $F$ is the set of accept states. 
\end{itemize}
\end{definition}

$\quad$\\[-1em]
\textbf{Example:}\\
Let's consider the following finite automaton.
\begin{figure}[H]
    \centering
    \includegraphics[width=0.4\linewidth]{Pictures/finite_auto_1.png}
\end{figure}
$\quad$\\[-2em]
Here, $M_1=(Q,\Sigma,\delta,q_1,F)$ is a finite automaton. For sake of example, here are the exact details of $M_1$.
\begin{itemize}
    \item $Q=\{q_1, q_2. q_3\}$
    \item $\Sigma=\{0, 1\}$
    \item $F=\{q_3\}$
\end{itemize}
It accepts a finite string as input. The output is either \textit{ACCEPT} or \textit{REJECT}.
The computation goes as follows:
\begin{enumerate}
    \item Begin at start state.
    \item Read input symbols.
    \item Follow corresponding transitions.
    \item \textit{ACCEPT} if we reach the accept state, otherwise \textit{REJECT}.
\end{enumerate}
For example: 01101 $\to$ \textit{ACCEPT}, while 00101 $\to$ \textit{REJECT}. Here, $M_1$ accepts all string in $A$ where $A=\{w|w\text{ contains substring }11\}$.
We say that \textbf{$A$ is the language of $M_1 \iff M_1$ recognizes $A \iff A=L(M_1)$}.

\subsubsection{Strings and languages}
A \textbf{string} is a finite sequence of symbols $w_1w_2\cdots w_n\in\Sigma$. A \textbf{language} is a set of string (finite or infinite).
The \textbf{empty string} $\varepsilon$ is the string of length 0. The \textbf{empty language} $\emptyset$ is the set with no strings.
\begin{definition}[Accepting strings]
A finite automaton $M$ \textbf{accepts string} $w=w_1w_2\cdots w_n$ for each $w_i\in\Sigma$ 
if there exists a sequence of states $r_0,r_1,\dots,r_n\in Q$ where:
\begin{itemize}
    \item $r_0=q_0$
    \item $r_i=\delta(r_{i-1},w_i)$ for $1\leq i\leq n$
    \item $r_n\in F$
\end{itemize}
\end{definition}
\begin{definition}[Regular language]
We say a language is $\textbf{regular}$ if some finite automaton recognizes it.
\end{definition}
$\quad$\\[-1em]
\textbf{Example 1:}
\begin{figure}[H]
    \centering
    \includegraphics[width=0.4\linewidth]{Pictures/finite_auto_1.png}
\end{figure}
$\quad$\\[-1em]
$L=(M_1)=\{w|w\text{ contains substring }11\}=A$. Therefore, $A$ is regular.
\\\\
\textbf{Example 2:}\\
Let $B=\{w|w\text{ has an even number of 1s}\}$. In this case, $B$ is regular. (not shown)
\\\\
\textbf{Example 3:}\\
Let $C=\{w|w\text{ has equal number of 0s and 1s}\}$. In this case, $C$ is not regular. (provable)

\subsubsection{Regular expressions}
\begin{definition}[Regular operations]
Let $A,B$ be languages.
\begin{itemize}
    \item \textbf{Union:} $A\cup B=\{w|w\in A\text{ or }w\in B\}$.
    \item \textbf{Concatenation:} $A\circ B=\{xy|x\in A \text{ and }y\in B\}=AB$.
    \item \textbf{Star:} $A^{\ast}=\{x_1\dots x_k|x_i\in A\text{ for }k\geq 0\}$. (Note: $\varepsilon\in A^{\ast}$)
\end{itemize}
\end{definition}
$\quad$\\[-1em]
Regular expressions are built from $\Sigma,\emptyset,\varepsilon$ by using regular operations $\cup,\circ,\ast$.
\\\\
\textbf{Example 1:}
\begin{itemize}
    \item $(0\cup 1)^{\ast}=\Sigma^{\ast}$ gives all strings over $\Sigma$.
    \item $\Sigma^{\ast}1$ gives all strings that end with 1.
    \item $\Sigma^{\ast}11\Sigma^{\ast}$ gives all strings that contain $11=L(M_1)$.
\end{itemize}
\textbf{Example 2:}\\
Let $A=\{\text{good, bad}\}$ and $B=\{\text{boy, girl}\}$.
\begin{itemize}
    \item $A\cup B=\{\text{good, bad, boy, girl}\}$.
    \item $A\circ B=AB=\{\text{goodboy, goodgirl, badboy, badgirl}\}$.
    \item $A^{\ast}=\{\varepsilon, \text{good, bad, goodgood, goodbad, badgood, badbad, goodgoodgood, }\dots\}$
\end{itemize}

\subsubsection{Nondeterministic finite automata}
\begin{definition}[Nondeterministic finite automata]
A \textbf{nondeterministic finite automata (NFA)} $N$ is a 5-tuple $(Q,\Sigma,\delta,q_0,F)$ where
everything is the exact same as a DFA except $\delta$. Here,
$\delta:Q\times\Sigma_{\varepsilon} \to \mathcal{P}(Q)=\{R\hspace{2px}|\hspace{2px} R\subseteq Q\}$.
\end{definition}
$\quad$\\[-1em]
New features of nondeterminism:
\begin{itemize}
    \item Multiple paths possible (0, 1, or many at each step)
    \item $\varepsilon$-transition is a "free" move without reading input.
    \item Accept input if \textbf{some} path leads to the accept state.
\end{itemize}
Nondeterminism doesn't correspond to a physical machine we can build. However, it if useful mathematically.
Here are some ways to think about it:
\begin{itemize}
    \item \textbf{Computationally:} Fork new parallel thread and accept if any thread leads to an accept state.
    \item \textbf{Mathematically:} Tree with branches. Accept if any branch leads to an accept state.
    \item \textbf{Magical:} Guess at each nondeterministic step which way to go. The machine always makes the right guess that leads to the accept state, if possible.
\end{itemize}

\end{figure}
$\quad$\\[-1em]

If an NFA recognizes $A$, then $A$ is regular.

\textbf{Proof:}\\
Let NFA $N=(Q,\Sigma,\delta,q_0,F)$ recognize $A$. We need to construct a DFA $M=(Q',\Sigma,\delta',q_0',F')$, ignoring the $\varepsilon$-transitions.

\begin{itemize}

    \item $\delta'(R\in Q',a)=q\in\delta(r,a)$ for some $r\in R$.
    \item $q_0'=\{q_0\}$.
    \item $F'=\{R\in Q'|R\cap F\}$.
\end{itemize}

\begin{note_special}[Theorem: Closure under $\cup$.]
If $A_1$ and $A_2$ are regular languages, then so is $A_1\cup A_2$.

    \item $\delta((q,r),a)=\big(\delta_1(q,a),\delta_2(q,a)\big)$.
    \item $F=(F_1\times Q_2)\times(Q_1\times F_2)$.
\end{itemize}

\subsubsection{Non-regular languages}
How do we show a language is not regular?
\begin{itemize}
    \item Remember, to show a language is \textit{regular}, we give an equivalent DFA.
    \item To show a language is \textit{not regular}, we must give a proof.
    \item It is not enough to say you couldn't find a DFA for it, therefore it isn't regular!
\end{itemize}
\textbf{Example 1:}\\
Let $B=\{w|w\text{ has equal numbers of 0s and 1s}\}$. One's intuition syas that $B$ is not regular since DFAs cannot count unboundedly.
\\\\
\textbf{Example 2:}\\
Let $C=\{w|w\text{ has equal numbers of 01 and 10 substrings}\}$. As examples, $0101\not\in C$ and $0110\in C$.
Again, one's intuition says that $C$ is not regular since DFA cannot count unboundedly.
However, $C$ is regular!

\subsubsection{Proving non-regularity}
\begin{note_special}[Pumping Lemma]
For every regular language $A$, there exists a number $p$, called the "pumping length", such that if $s\in A$ and $|s|\ge p$ then $s=xyz$ where
\begin{enumerate}
    \item $xy^{i}z\in A$ for all $i\ge 0\quad$ ($y^{i}=\underbrace{yy\cdots y}_i$).
    \item $y\ne\varepsilon$.
    \item $|xy|\le p$.
\end{enumerate}
Informally, if $A$ is regular, then every long string in $A$ can be "pumped" and the result stays in $A$.
\\\\
\textbf{Proof:}\\
Let DFA $M$ recognize $A$. Let $p$ be the number of states in $M$. Pick $s\in A$ where $|s|\ge p$.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.4\linewidth]{Pictures/nonr_1.png}
\end{figure}

$M$ will repeat a state $q_j$ when reading $s$ because $s$ is so long.
The path that $M$ follows when reading $s$.
\begin{figure}[H]
    \centering
    \includegraphics[width=0.4\linewidth]{Pictures/nonr_2.png}
\end{figure}
\end{note_special}
$\quad$\\[-1em]
\textbf{Exmaple 1:}\\
Let $D=\{0^k1^k|k\ge 0\}$. Show that $D$ is not regular.
\\\\
Assume, for the sake of contradiction, that $D$ is regular. \\
Since $D$ is regular, the pumping lemma must hold. Let $s=0^p1^p\in D$. \\
The pumping lemma says that we can divide $s=xyz$. \\
But $xyyz$ has excess 0s, and thus $xyyz\not\in D$ contradicting the pumping lemma. \\
Therefore, our assumption is false and thus $D$ is not regular.

$\quad$\\[-1em]
\textbf{Example 2:}\\
Let $F=\{ww|w\in\Sigma^{\ast}\}$. Say $\Sigma^{\ast}=\{0,1\}$. Show that $F$ is not regular.
\\\\
Assume, for the sake of contradiction, that $F$ is regular. \\
Since $F$ is regular, the pumping lemma must hold. \\
We need to choose $s\in F$. Let $s=0^p10^p1\in F$. \\
We can show that $s=xyz$ cannot be pumped satisfying the 3 conditions. \\
Thus, $xyyz\not\in F$, which is a contradiction. Therefore, $F$ is not regular.
\\\\
\textbf{Example 3:}\\
Let $B=\{w|w\text{ has equal numbers of 0s and 1s}\}$. Show that $B$ is not regular.
\\\\
Assume, for the sake of contradiction, that $B$ is regular. \\
We know $0^{\ast}1^{\ast}$ is regular, and so $B\cap 0^{\ast}1^{\ast}$ is regular (closure under intersection). \\
But $D=B\cap 0^{\ast}1^{\ast}$ and we already showed $D$ is not regular (from example 1). \\
Therefore, $B$ is not regular.
\\\\
\textbf{Example 4:}\\
Let $A=\{1^{n^2}|n\ge 0\}$. \textit{($A$ contains all strings of 1s whose length is a perfect square)}. Show that $A$ is not regular.
\\\\
Assume, for the sake of contradiction, that $A$ is regular.\\
Let $p$ be the pumping length given by the pumping lemma. Take $s=1^{p^2}\in A$.\\
The pumping lemma guarantees $s=xyz$ with $s=xy^iz\in A$ for some $i\ge 0$.\\
Consider the two strings $xyz$ and $xy^2z$. The length of these strings differ by $y$.\\
By contition 3, $|xy|\le p$ and thus $|y|\le p$. Then, we have $|xyz|=p^2$ and so $|xy^2z|\le p^2+p$.\\
But $p^2+p<p^2+2p+1=(p+1)^2$.\\
Moreover, condition 2 implies that $y$ is not the empty string and so $|xy^2z|>p^2$.\\
Therefore, the length of $xy^2z$ lies strictly between the consecutive squares $p^2$ and $(p+1)^2$.\\
Hence this length cannot be a perfect square itself, which is a contradiction.\\
Thus, $xy^2z\not\in A$ and so we conclude that $A$ is not regular.
\\\\
\textbf{Example 5:}\\
Let $E=\{0^i1^j|i>j\}$. Show that $E$ is not regular.
\\\\
Assume, for the sake of contradiction, that $E$ is regular.\\
Let $p$ be the pumping length given by the pumping lemma. Take $s=0^{p+1}1^p\in E$.\\
By condition 1, $xy^iz\in E$ even when $i=0$. Consider the string $xy^0z=xz$.\\
Removing string $y$ decreases the number of 0s in $s$.\\
But, recall that $s$ has just one more 0 than 1.\\
Therefore, $xz$ cannot have more 0s than 1s and so $s=0^{p+1}1^p\not\in E$. \\
Hence a contradiction. Therefore, $E$ is not regular.
\subsection{Context-free languages}
\subsubsection{Context-free grammars}
\begin{definition}[Context-free grammar]
A \textbf{Context Free Grammar (CFG)} $G$ is a 4-tuple $(V,\Sigma,R,S)$ where
\begin{itemize}
    \item $V$ is the finite set of variables.
    \item $\Sigma$ is the finite set of terminal symbols.
    \item $R$ is the finite set of rules (rule form: $V\to (V\cup \Sigma)^{\ast}$).
    \item $S$ the starting variable.
\end{itemize}
For $u,v\in(V\cup\Sigma)^{\ast}$ write
\begin{enumerate}
    \item $u\Rightarrow v$ if you can go from $u$ to $v$ with one substitution step in $G$.
    \item $u\overset{\ast}{\Rightarrow} v$ if you can go from $u$ to $v$ with some number of substitution steps in $G$. \\
    $u\Rightarrow u_1\Rightarrow u_2\Rightarrow \cdots\Rightarrow u_k\Rightarrow v$ is called a \textit{derivation} of $v$ from $u$.
    Furthermore, if $u=S$ then it is a \textit{derivation} of $v$.
\end{enumerate}
$L(G)=\{w|w\in\Sigma^{\ast}\text{ and }S\overset{\ast}{\Rightarrow} w\}$.
\end{definition}
\begin{definition}[Context-free language]
$A$ is a \textbf{Context Free Language (CFL)} is $A=L(G)$ for some CFG $G$.
\end{definition}

\subsubsection{Ambiguity}
Take the following two CFGs:\\
\begin{minipage}{0.5\textwidth}
\begin{flalign*}
G_1& &\\
E&\rightarrow E+T\hspace{4px}|\hspace{4px} T &\\
T&\rightarrow T\times F\hspace{4px}|\hspace{4px} F &\\
F&\rightarrow (E)\hspace{4px}|\hspace{4px} a
\end{flalign*}
\end{minipage}
\begin{minipage}{0.5\textwidth}
\begin{flalign*}
G_2& &\\
E&\rightarrow E+E\hspace{4px}|\hspace{4px}E\times E\hspace{4px}|\hspace{4px}(E)\hspace{4px}|\hspace{4px}a
\end{flalign*}
\end{minipage}
$\quad$\\\\[-1em]
Both $G_1$ and $G_2$ recognize the same language, i.e. $L(G_1)=L(G_2)$.
However, $G_1$ is an unambiguous CFG and $G_2$ is ambiguous.

\subsubsection{Pushdown automaton}
\begin{definition}[Pushdown automaton]
A \textbf{Pushdown Automaton (PDA)} is a 6-tuple $(Q,\Sigma,\Gamma,\delta,q_0,F)$:
\begin{itemize}
    \item $\Sigma$ is the input alphabet.
    \item $\Gamma$ is the stack alphabet.
    \item $\delta:Q\times \Sigma_{\varepsilon}\times\Gamma_{\varepsilon}\rightarrow\mathcal{P}(Q\times\Gamma_{\varepsilon})$\\
    $\delta(q,a,c)=\{(r_1,d),(r_2,e)\}$
\end{itemize}
We accept if some thread is in the accept state at the end of the input string.
\end{definition}
$\quad$\\[-1em]
A PDA operates like an NFA except can write/add (push) or read/remove (pop) symbols from the top of the stack.
The input appears on a tape.
\\\\
\textbf{Example 1:}\\
PDA for $D=\{0^k1^k:k\ge 0\}$
\begin{enumerate}
    \item Read 0s from input, push 0 onto the stack until a 1 is read.
    \item Read 1s from input, while popping 0s from the stack.
    \item Enter the accept state if the stack is empty.
\end{enumerate}
\begin{figure}[H]
    \centering
    \includegraphics[width=0.5\linewidth]{Pictures/pda_1.png}
\end{figure}
\begin{note}[How to read transitions for PDAs]
\textbf{Example 1:} Take the transition $\varepsilon,\hspace{2px}\varepsilon;\hspace{2px}\$$. 
\begin{itemize}
    \item The first $\varepsilon$ is the input read from the tape. Since we're reading $\varepsilon$, this is equivalent to a blank on the tape.
    \item The second $\varepsilon$ is the value on the top of the stack. Since we're reading $\varepsilon$, we assume the stack is empty.
    \item The last $\$$ is part of the stack alphabet. This signifies the bottom of the stack. We want to "push" this value onto the stack.
\end{itemize}
\textbf{Example 2:} Take the transition $\varepsilon,\hspace{2px}\$;\hspace{2px}\varepsilon$. 
\begin{itemize}
    \item The first $\varepsilon$ is the input read from the tape. Since we're reading $\varepsilon$, this is equivalent to a blank on the tape.
    \item The $\$$ is the value we expect on the top of the stack. 
    \item The second $\varepsilon$ is the value we push onto the stack. We're effectively replacing the bottom-of-stack character with a blank, clearing the stack.
\end{itemize}
\end{note}
\textbf{Example 2:}\\
PDA for $B=\{ww^{\mathcal{R}}:w\in\{0,1\}^{\ast}\}$ with sample input: 011110.
\begin{enumerate}
    \item Read and push input symbols onto the stack. Non-deterministically either repeat or go to (2).
    \item Read input symbols and pop stack symbols, and compare. If they are ever not equal, then the thread rejects.
    \item Enter the accept state if the stack is empty.
\end{enumerate}

\subsubsection{Converting CFGs to PDAs}
\begin{note_special}[Theorem]
If $A$ is a CFG, then some PDA recognizes $A$.
\\\\
\textbf{Proof:}\\
Convert $A$'s CFG to a PDA.
\begin{figure}[H]
    \centering
    \includegraphics[width=0.5\linewidth]{Pictures/pda_2.png}
\end{figure}
\begin{enumerate}
    \item Push the start symbol onto the stack.
    \item If the top of the stack is:
    \begin{itemize}
        \item \textit{Variable:} replace with right hand side of rule (non-deterministic choice).
        \item \textit{Terminal:} pop it  and match with next input symbol.
    \end{itemize}
    \item If the stack is empty, enter the accept state.
\end{enumerate}
\end{note_special}

\subsubsection{Equivalence of CFGs and PDAs}
\begin{note_special}[Theorem]
$A$ is a CFL if and only if some PDA recognizes $A$. \textit{(Proof not examinable)}
\end{note_special}
\begin{note_special}[Corollaries]
\begin{enumerate}
    \item Every regular language is a CFL.
    \item If $A$ is a CFL and $B$ is regular, then $A\cap B$ is a CFL.
\end{enumerate}
\textbf{Note 1:} If $A$ and $B$ are CFLs then $A\cap B$ may not be a CFL. Therefore, the class of CFLs is not closed under $\cap$.
\\
\textbf{Note 2:} The class of CFL is closed under $\cup,\circ,\ast$.
\end{note_special}

\subsubsection{Chomsky normal form (CNF)}
Chomsky normal form is a simplification of grammars:
\begin{itemize}
    \item If the start symbol is recursive, remove it.
    \item Removing $\varepsilon$-productions.
    \item Removing unit productions.
    \item Removing "useless" productions.
\end{itemize}
\begin{note_special}[Converting to CNF]
Given a grammar $G=\{V,T,S,P\}$, we can derive $G'=\{V,T,S',P'\}$ as follows:
\\\\
\textbf{Removing recursive start symbol:}\\
Introduce a new start symbol $S'$. Let $P'$ be the production rule set $P$ of $G$ with the following rule added to it: $S'\rightarrow S$. 
\\\\
\textbf{Remove $\varepsilon$-productions:}\\
If there is a production of the form $A\rightarrow\varepsilon$ then $A$ is a nullable variable.
If $B\rightarrow A_1A_2\cdots A_n$ and $A_1A_2\cdots A_n$ are nullable variables, then $B$ is also a nullable variable.
A given grammar $G$ can be converted into a grammar $G'$ that does not contain nullable variables.
\begin{enumerate}
    \item Remove each productions rule of the form $A\rightarrow\varepsilon$.
    \item Add each rule of the form $A\rightarrow s_1s_2\cdots s_n$ with $s_i\in V\cup T$ such that each $s_i$ is not a nullable variable to $P'$.
    \item For each production rule $A\rightarrow s_1N_1s_2N_2\cdots s_nN_n$, where each $s_i$ is not a nullable variable and $N_1,N_2,\dots,N_n$ are nullable variables, add a copy of the rule with one or more $N_i$'s replaced by $\varepsilon$ to $P'$, e.g. $A\rightarrow s_1s_2N_2\cdots s_nN_n$.
    Note that if the $s_i$'s are also nullable, then we do not add $A\rightarrow\varepsilon$ unless $A$ is the start symbol.
\end{enumerate}
\textbf{Remove unit productions:}
\begin{itemize}
    \item Draw a dependency graph with edge $(A,B)$ for each unit production of the form $A\rightarrow B$.
    \item From the graph, identify all $A$ $B$.
    \item For all $A$ and $B$ identified, add a production of the form $A\rightarrow s_1\hspace{4px}|\hspace{4px}s_2\hspace{4px}|\hspace{4px}\cdots\hspace{4px}|\hspace{4px} s_n$ to $P'$ where
    $B\rightarrow \vec{s_1\hspace{4px}|\hspace{4px}s_2\hspace{4px}|\hspace{4px}\cdots\hspace{4px}|\hspace{4px} s_n}$. Note that each $s_i\in V\cup T$ and none of the $s_i$ form unit productions.
\end{itemize}
\textbf{Remove useless productions:}\\
There are essentially two types of useless productions:
\begin{itemize}
    \item Productions containing variables that do not terminate.
    \item Productions containing variables that are not reachable.
\end{itemize}
Identify these productions are remove them from $P'$.
\\\\
\textbf{Correct production rule format:}\\
A context-free grammar $G$ is in CNF, if the production rules have the following form:
\begin{itemize}
    \item $A\rightarrow AB$ where $A$ and $B$ are variables, or
    \item $A\rightarrow a$ where $a$ is a single terminal.
\end{itemize}
\end{note_special}
\textbf{Example:}\\
Take the following grammar:
\begin{flalign*}
S&\rightarrow ASA\hspace{4px}|\hspace{4px}aB &\\
A&\rightarrow B\hspace{4px}|\hspace{4px}S &\\
B&\rightarrow b\hspace{4px}|\hspace{4px}\varepsilon
\end{flalign*}
\textbf{Step 1: Remove recursive start symbol}
\begin{flalign*}
S'&\rightarrow S &\\
S&\rightarrow ASA\hspace{4px}|\hspace{4px}aB &\\
A&\rightarrow B\hspace{4px}|\hspace{4px}S &\\
B&\rightarrow b\hspace{4px}|\hspace{4px}\varepsilon
\end{flalign*}
\textbf{Step 2: Remove $\varepsilon$-productions}
\begin{flalign*}
S'&\rightarrow S &\\
S&\rightarrow ASA\hspace{4px}|\hspace{4px}aB\hspace{4px}|\hspace{4px}AS\hspace{4px}|\hspace{4px}SA\hspace{4px}|\hspace{4px}S\hspace{4px}|\hspace{4px}a &\\
A&\rightarrow B\hspace{4px}|\hspace{4px}S &\\
B&\rightarrow b
\end{flalign*}
\textbf{Step 3: Remove unit productions}
\begin{flalign*}
S'&\rightarrow ASA\hspace{4px}|\hspace{4px}aB\hspace{4px}|\hspace{4px}AS\hspace{4px}|\hspace{4px}SA\hspace{4px}|\hspace{4px}a &\\
S&\rightarrow ASA\hspace{4px}|\hspace{4px}aB\hspace{4px}|\hspace{4px}AS\hspace{4px}|\hspace{4px}SA\hspace{4px}|\hspace{4px}a &\\
A&\rightarrow b\hspace{4px}|\hspace{4px}ASA\hspace{4px}|\hspace{4px}aB\hspace{4px}|\hspace{4px}AS\hspace{4px}|\hspace{4px}SA\hspace{4px}|\hspace{4px}a &\\
B&\rightarrow b
\end{flalign*}
\textbf{Step 4: Ensure correct production rule format}
\begin{flalign*}
S'&\rightarrow AA1\hspace{4px}|\hspace{4px}UB\hspace{4px}|\hspace{4px}AS\hspace{4px}|\hspace{4px}SA\hspace{4px}|\hspace{4px}a &\\
S&\rightarrow AA1\hspace{4px}|\hspace{4px}UB\hspace{4px}|\hspace{4px}AS\hspace{4px}|\hspace{4px}SA\hspace{4px}|\hspace{4px}a &\\
A&\rightarrow b\hspace{4px}|\hspace{4px}AA1\hspace{4px}|\hspace{4px}UB\hspace{4px}|\hspace{4px}AS\hspace{4px}|\hspace{4px}SA\hspace{4px}|\hspace{4px}a &\\
A1&\rightarrow SA &\\
U&\rightarrow a &\\
B&\rightarrow b
\end{flalign*}

\subsubsection{Proving languages are not context free}
\begin{note_special}[Pumping Lemma for CFLs]
For every CFL $A$, there is a $p$ such that if $s\in A$ and $|s|\ge p$ then $s=uvxyz$ where
\begin{enumerate}
    \item $uv^ixy^iz\in A$ for all $i\ge 0$.
    \item $vy\neq\varepsilon$.
    \item $|vxy|\le p$.
\end{enumerate}
Informally, all long string in $A$ are pumpable and stay in $A$.
\end{note_special}
$\quad$\\[-1em]
\textbf{Example 1:}\\
Let $B=\{0^k1^k2^k|k\ge 0\}$. Show that $B$ is not a CFL.
\\\\
Assume, for the sake of contradiction, that $B$ is a CFL.\\
The CFL pumping lemma gives $p$ as above. Let $s=0^p1^p2^p\in B$.\\
The pumping lemma says that we can divide $s=uvxyz$ satisfying the 3 conditions.\\
Condition 3 ($|vxy|\le p$) implies that $vxy$ cannot contain both 0s and 2s.\\
So $uv^2xy^2z\not\in B$, violating condition 1, which is a contradiction.\\
Therefore, our assumption is false. We conclude that $B$ is not a CFL.
\\\\
\textbf{Example 2:}\\
Let $F=\{ww|w\in\Sigma^{\ast}\}$ where $\Sigma=\{0,1\}$. Show that $F$ is not a CFL.
\\\\
Assum, for the sake of contradiction, that $F$ is a CFL.\\
The CFL pumping lemma gives $p$ as above. Take $s=0^p1^p0^p1^p\in F$.\\
Condition 3 implies that $vxy$ does not overlap two runs of 0s or two runs of 1s.\\
Therefore, in $uv^2xy^2z$, two runs of 0s or two runds of 1s have unequal length.\\
So $uv^2xy^2z\not\in F$ violating Condition 1, which is a contradiction.\\
Thus, $F$ is not a CFL.

\subsection{Turing Machines}
\subsubsection{Turing machines}
\begin{definition}[Turing machines]
A \textbf{turing machine} $M$ is a 7-tuple $(Q,\Sigma,\Gamma,\delta,q_0,\square,F)$ where:
\begin{itemize}
    \item $Q$ is the set of states.
    \item $\Sigma$ is the input alphabet \textit{(finite)}.
    \item $\Gamma$ is the tape alphabet \textit{(finite)}.
    \item $\delta$ is the transition function.
    \item $q_0\in Q$ is the initial/start state.
    \item $F\subseteq Q$ is the final state(s).
    \item $\square\in\Gamma$ is the blank symbol.
\end{itemize}
\begin{figure}[H]
    \centering
    \includegraphics[width=0.6\linewidth]{Pictures/tm_1.png}
\end{figure}
\end{definition}
$\quad$\\[-1em]
There some conditions:
\begin{itemize}
    \item $\Sigma\subseteq\Gamma$, since the input is written on the tape initially.
    \item $\square\in\Gamma\setminus\Sigma$, since the rest of the tape is blank.
\end{itemize}
Initially, we're in state $q_0$. The tape contains input $w$ surrounded by $\square$.
The tape head is in the left-most cell of the input also denoted with $D$. The transitions work as follows:
\begin{itemize}
    \item $\delta:Q\times\Gamma\Rightarrow Q\times\Gamma\times\{L,R\}$.
    \item $\delta(q,x)=(p,y,d)$ means that if $M$ is in state $q$ and the tape head is over symbol $x$, then $M$:
    \begin{enumerate}
        \item Changes state to $p$.
        \item Replaces $x$ by $y$ on the tape.
        \item Moves the tape head by one cell in a direction $d$ \textit{(Either left or right)}.
    \end{enumerate}
\end{itemize}

\subsubsection{Determinism}
A turing machine is \textbf{deterministic} if, for each $\delta(q,x)$ we have at most one move \textit{($\delta(q,x)$ could also be undefined)}.
\\\\
\textbf{Acceptance:}\\
$w$ is accepted by a turing machine $M$ if $M$, when started with $w$ on the tape, eventually enters a final state. We can assume that all final states are halting, i.e. no transition is defined for them.
\\\\
\textbf{Rejection:}\\
$M$ halts in non-final states. In other words, in states for which no transition is defined, or it never halts \textit{(Infinite loop)}.

\subsubsection{Instantaneous descriptions}
This is the configuration of a turing machine. It describes the current situation of the turing machine (and the tape).
$$
\text{ID}=\propto q\beta\text{ with }q\in Q,\propto_1,\propto_2\in\Gamma^{\ast}
$$
Meaning:
\begin{itemize}
    \item The non-blank portion of the tape contains $\propto,\beta$.
    \item The head is on the left-most symbol of $\beta$.
    \item The machine is in state $q$.
\end{itemize}
We will use $\vdash$ and $\vdash^{\ast}$ to denote the changes.

\subsubsection{Language accepted by a turing machine}
Let $M=(Q,\Sigma,\Gamma,\delta,q_0,\square,F)$ be a turing machine. Then, the language accepted by $M$ is
$$
L(M)=\{w\in\Sigma^{\ast}|q_0w\vdash^{\ast}\propto p\beta\text{ with }p\in F\text{ and }\propto_1\beta\in\Gamma^{\ast}\}
$$
The set of all languages we can accept using a turing machine is often called the recursively enumerable languages.
Conversely, a turing machine can accept a language by halting:
$$
H(M)=\{w\in\Sigma|q_0q\vdash^{\ast}\propto p\beta\text{ where there is no possible move from}\propto p\beta\}
$$
